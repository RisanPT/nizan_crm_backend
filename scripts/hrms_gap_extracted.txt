01 S E C T I O N O N E
Executive summary
Three findings drive the plan.
1. Attendance and payroll are the strongest asset
A live Timebox integration, a draft → approve → pay salary workflow, a separate HRA module and a 5-pillar performance
scorecard all ship today. v2 should extend these, not rebuild them.
2. Leave is a mock screen
leave_request_screen.dart renders hard-coded rows and makes zero API calls. There is no Leave model, route or
controller anywhere in the backend — though a leave permission key is already reserved in Role.PERMISSION_KEYS .
W H Y T H I S M AT T E R S M O S T
This is the single most visible gap, because it looks finished. The screen has a working “New Leave Request”
bottom sheet, a leave-type dropdown and a history list — and it persists nothing. A user can file a request and
watch it vanish.
3. Five modules exist only as free text
Recruitment, training, engagement, conflict and offboarding appear solely as manually-entered fields in the HR month-
end report ( deptReportController.js ). Someone types “apps→interviews→offers→joins” into a box each month. There
is no underlying data.
R E C O M M E N D AT I O N
Build v2 in four phases over roughly 14–18 weeks, starting with the employee master record and leave — the two
things every other module depends on — before opening the recruitment and offboarding greenfield.

The Timebox dependency is the key architectural fact
Attendance is not owned by this system. timeboxController.js pulls punches and monthly summaries from Timebox,
matches them to CRM employees via Employee.timeboxEmployeeId , and drives payroll from the result.
POST /api/timebox/sync-employees writes Timebox IDs back onto employee records so renames never break payroll
— a deliberate, well-made decision.
C O N S E Q U E N C E F O R V 2
Leave, overtime and LOP all depend on data Timebox holds. Any leave module must reconcile with Timebox’s day-
status, or the two systems will disagree about whether 14 March was an absence or approved leave.
RBAC and org structure are already solid
Role carries a key , a permission array drawn from 21 PERMISSION_KEYS , and a homeRoute . Department models
nine seed departments across two divisions, each with a head (an Employee , so Timebox-imported staff qualify), a
delegation boundary ( allowedRoleKeys ) and geography scoping. User links to both Employee and Department .
v2 needs no new access-control machinery — only new permission keys.

Architecture decisions
The employee lifecycle is the spine
Today the eight requested modules would be eight disconnected screens. They are one flow, and
Employee.employmentStatus is the state machine that joins them.
Candidate 	Interviewing 	Offered 	Probation
Shortlisted 	Round 3 cleared 	Offer accepted
R E Q U I S I T I O N A P P R O V E D
Orientation done + review passed
Confirmed 	Notice period 	Exited
Resignation 	Clearance done
Recruitment Employment 	Exit
The employee lifecycle state machine, driven by Employee.employmentStatus
T H E J O I N T H AT M A K E S R E C R U I T M E N T W O R T H B U I L D I N G
Accepting an offer should create the Employee record from the Candidate record — name, email, phone,
designation, department and joining date all carry across. Without that link, recruitment is a data-entry exercise
that HR redoes by hand.
Draw the Timebox boundary explicitly
Approved leave must be visible to the payroll calculation, or LOP will be wrong. There are two options:
1. Push — on leave approval, write the day status back to Timebox. Cleanest, but depends on Timebox exposing a write
API. This needs to be confirmed before Phase 2 starts.
2. Overlay — keep leave local and have timeboxController subtract approved leave days from the absence count
before computing absenceDeduction . Works with a read-only Timebox, but risks the two systems disagreeing on
screen.
Default to the overlay unless Timebox write access is confirmed. Either way, the reconciliation belongs in one place — a
services/attendanceReconciler.js — not spread across controllers.
Make the payroll engine explicit
Payroll logic currently lives inside timeboxController.js alongside HTTP handling. Adding EPF, ESI, LOP and overtime
to that file will make it unmaintainable. Extract a services/payrollEngine.js that takes an employee, a period and an
attendance summary and returns a fully itemised salary — pure, testable, and the single place statutory rules live.

This is the one piece of v2 that warrants unit tests before anything else, because statutory errors are expensive and
silent.
Reuse the Ticket pattern for grievances, but not the Ticket model
Ticket already proves the shape: numbered record, department routing, assignment, status workflow, activity[]
audit trail, resolution fields. Grievance should copy that shape and add what HR needs and IT does not — a
confidential flag that restricts visibility to HR and the CEO, and an againstEmployeeId that must never be visible to
the accused party’s own manager by default.
New permission keys
PERMISSION_KEYS in models/Role.js must stay in sync with lib/core/auth/app_permissions.dart . Add
recruitment , training , engagement , grievance and offboarding . The leave key is already reserved and
unused — wire it up in Phase 1.
Employee self-service is a v2 question, not a v2 assumption
Every module in the ask is written from HR’s point of view. But leave requests, grievances and payslip access are things
employees do for themselves. The User ↔ Employee link already exists, so the plumbing is there. Whether v2 ships an
employee-facing portal changes the effort materially — see the open questions.
